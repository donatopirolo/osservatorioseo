> DOMANDA DI BREVETTO · US20240289407A1

Ricerca conversazionale con stato persistente tra i turni

Titolo originale: Search with stateful chat

Il brevetto descrive un sistema per affiancare una sessione di ricerca tradizionale con una chat dotata di stato persistente ("generative companion") che mantiene e aggiorna il contesto dell'utente attraverso più turni. A ogni turno, il sistema classifica la query e lo stato dell'utente per selezionare zero, uno o più modelli generativi downstream (creativi, di sintesi, di chiarimento) e generare risposte personalizzate che tengono conto dell'intera traiettoria della sessione.

> COSA RIVENDICA

La rivendicazione indipendente 1 descrive un metodo implementato durante una sessione di ricerca di un utente che comprende: ricevere una query associata a un client device; recuperare informazioni contestuali associate all'utente o al dispositivo; generare output di un modello generativo (GM) processando, tramite un GM, dati indicativi della query e delle informazioni contestuali; generare una o più query sintetiche utilizzando l'output del GM; selezionare un set di documenti di risultati di ricerca (SRD), includendo nel set una pluralità di SRD query-responsive che rispondono sia alla query che alle query sintetiche; processare dati di stato indicativi della query, delle informazioni contestuali, delle query sintetiche e del set di SRD per identificare una classificazione della query; in base alla classificazione, selezionare uno o più GM downstream; generare uno o più output GM aggiuntivi processando, tramite i GM downstream selezionati, almeno parte dei dati di stato; e causare la renderizzazione di contenuto responsive alla query sul client device.

Le rivendicazioni dipendenti 2-16 specificano che le informazioni contestuali possono includere: query precedenti emesse durante la sessione (rivendicazione 2); dati estratti da pagine di risultati restituite in risposta a query precedenti (rivendicazione 3); dati estratti da SRD responsive a query precedenti (rivendicazione 4); informazioni sulla pianificazione dell'utente (rivendicazione 5), recuperate da calendari elettronici o corrispondenza dell'utente o di altri (rivendicazione 6); coordinate di posizione dell'utente (rivendicazione 7). I dati di stato possono essere un embedding aggregato generato da query, informazioni contestuali, query sintetiche e set di SRD (rivendicazione 8), o includere dati estratti da SRP restituite in risposta alle query sintetiche (rivendicazione 9), o dati indicativi di azioni eseguite dall'utente dopo l'emissione della query (rivendicazione 10), inclusi dati estratti da SRD accessati dall'utente (rivendicazione 11). I GM downstream possono includere: un GM creativo addestrato a generare linguaggio naturale creativo (rivendicazione 12); un GM ambient addestrato a generare sintesi di documenti accessati dall'utente dopo l'emissione della query (rivendicazione 13); un GM di risultati di ricerca addestrato a generare sintesi di pagine di risultati (rivendicazione 14). Il contenuto responsive alla query può essere incluso nelle informazioni contestuali recuperate durante turni successivi della sessione (rivendicazione 15), e le informazioni contestuali possono includere contenuto responsive precedente a una query precedente emessa durante la sessione (rivendicazione 16). Le rivendicazioni 17-20 sono rispettivamente una rivendicazione di sistema e di supporto leggibile da computer che replicano sostanzialmente la rivendicazione 1.

> LETTURA SEO (INTERPRETAZIONE)

La descrizione contempla un sistema chiamato "generative companion" che mantiene uno stato dell'utente ("user state", paragrafi relativi a FIG. 8 e blocco 871) attraverso più turni di una sessione di ricerca. Questo stato può essere rappresentato come embedding semanticamente ricchi o come strutture dati contenenti query precedenti, token, keyword (paragrafi su user state 871). Il sistema può recuperare informazioni contestuali da calendari elettronici, corrispondenza, posizione GPS, attività corrente rilevata da accelerometro/giroscopio, applicazioni in primo piano, e contenuto di SRP e SRD precedenti (paragrafi su context engine 113 e user state 871).

La descrizione contempla l'uso di un primo LLM (blocco 150, context engine 113) per generare query sintetiche o "riformulate" che possono essere query alternative, query supplementari, versioni riscritte della query dell'utente o query di drill-down (paragrafi su synthetic queries). Queste query sintetiche vengono eseguite da un motore di ricerca per ottenere SRD (blocco 960, search system 160). I dati di stato vengono poi processati, utilizzando uno o più modelli di machine learning o classifier (blocco 152), per classificare la query in una delle diverse categorie candidate (blocco 962). La descrizione elenca esempi di classificazioni: "needs creative text generation", "needs creative media generation", "can benefit from ambient generative summarization", "can benefit from SRP summarization", "would benefit from suggested next step query", "needs clarification", "do not interfere" (paragrafi su LLM selection engine 132 e FIG. 8).

In base alla classificazione, vengono selezionati uno o più LLM downstream (blocco 964, elementi 872A-F in FIG. 8). La descrizione contempla: creative text LLM (872A) addestrati a generare testo creativo come poesie o saggi; creative media generative models (872B) come modelli di diffusione per immagini, che possono incorporare contenuto personale dell'utente se autorizzato; ambient generative LLM (872C) addestrati a sintetizzare un documento specifico accessato dall'utente, con grounding e verifica degli attributi dal documento stesso; SRP generative LLM (872D) addestrati a sintetizzare SRP includendo passaggi di testo e immagini estratte o generate, potenzialmente con linkificazione come in FIG. 3; next step LLM (872E) addestrati a generare suggerimenti per query successive che guidano la sessione, inclusi suggerimenti per drill-down categorico o raccomandazioni di contenuti digitali; clarification LLM (872F) addestrati a generare domande di chiarimento quando termini ambigui non possono essere risolti tramite lo stato dell'utente (paragrafi su downstream LLMs e FIG. 8).

La descrizione contempla che l'output generato (blocco 968, current output 874) venga reso all'utente e che questo output venga incorporato nello stato dell'utente per i turni successivi (freccia da current output 874 a user state 871 in FIG. 8), creando un ciclo di feedback. La descrizione contempla anche che lo stato dell'utente possa essere salvato come "footprint" o "journey" di una sessione di ricerca, che può essere ripresa successivamente dall'utente o condivisa con altri (paragrafi su saving user state). La descrizione contempla che sessioni precedenti possano essere riprese esplicitamente o automaticamente in base alla similarità tra query corrente/stato corrente e stati di sessioni precedenti (paragrafi su resuming sessions).

Per la SEO, questo brevetto potrebbe indicare che Google stia sviluppando capacità di ricerca conversazionale che mantengono contesto attraverso più interazioni. Se implementato, potrebbe significare che i contenuti dovrebbero essere ottimizzati non solo per query singole ma per traiettorie di ricerca multi-turno. La capacità di generare query sintetiche potrebbe influenzare quali documenti vengono selezionati per sintesi, suggerendo che documenti responsive a variazioni e riformulazioni di una query potrebbero avere maggiore visibilità. La classificazione automatica delle query in categorie che richiedono diversi tipi di output generativo potrebbe significare che alcuni tipi di query riceverebbero sintesi testuali mentre altri riceverebbero output creativi o richieste di chiarimento, influenzando quali risultati vengono mostrati e come.

> COSA NON DIMOSTRA

  • Il brevetto è una domanda (A1) non ancora concessa e non dimostra che Google abbia implementato o implementerà questo sistema in Search.
  • Non specifica quali metriche o soglie vengano utilizzate dai classifier per assegnare le classificazioni delle query, né come vengano bilanciati i diversi segnali contestuali nello stato dell'utente.
  • Non dimostra che il mantenimento dello stato attraverso più turni migliori effettivamente la soddisfazione dell'utente o l'efficienza della ricerca rispetto a sessioni di ricerca tradizionali.
  • La descrizione contempla molteplici implementazioni opzionali ("in some implementations") senza indicare quali sarebbero effettivamente utilizzate in produzione.

> COSA FARE COMUNQUE

  1. Ottimizzare i contenuti per rispondere a variazioni e riformulazioni di query principali, non solo alla query esatta, dato che query sintetiche potrebbero essere generate e utilizzate per selezionare documenti.
  2. Strutturare i contenuti in modo che possano essere facilmente sintetizzati e verificati, con sezioni chiare e affermazioni supportate da evidenze, dato il focus su grounding e linkificazione.
  3. Considerare l'intero percorso informativo dell'utente su un argomento, non solo singole query isolate, nella pianificazione dei contenuti e della struttura del sito.
  4. Mantenere contenuti aggiornati e di alta qualità che possano essere considerati affidabili per sintesi automatiche, dato che trustworthiness e freshness sono menzionati come misure per la selezione di SRD.
